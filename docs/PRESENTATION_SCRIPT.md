## 2. 해커톤 주제와의 연결

### 발표 문장

> 이번 해커톤의 주제는  
> **‘AI와 미래의 공존: 무한한 상상, 무해한 AI’**입니다.
>
> 저희는 미래에 AI적 도구가 기기 이름을 분석하고 필요한 부품을 찾아 주어 사람의 제작을 도울 수 있다고 상상했습니다.
> 동시에 잘못된 연결이나 결과에 대한 과신을 예방하기 위해 판단 규칙과 경고 이유를 함께 보여 주고, 최종 결정은 사용자가 하도록 했습니다.

### 발표할 내용

- 사람과 AI가 공존하는 방법: AI적 도구는 정보를 비교하고 사람은 제작과 연결을 최종 결정합니다.
- 우리 팀의 새로운 상상: 기기 이름만으로 필요한 제작 부품을 찾아 주는 메이커 도우미입니다.
- 예방하려는 위험: 전압·인터페이스·기계 규격이 맞지 않는 부품의 무리한 연결입니다.
- 적용한 안전 장치: PASS, CHECK, FAIL과 경고 이유를 표시하고 참고 결과임을 안내합니다.

## 4. 앱 시연

### 시연 순서

1. 초기 화면을 보여 줍니다.
2. 사용자의 입력 또는 선택을 보여 줍니다.
3. 핵심 버튼을 누릅니다.
4. 결과와 판단 이유를 설명합니다.
5. 사용자가 최종적으로 선택할 수 있는 행동을 보여 줍니다.

### 시연에 사용할 입력

```text
기기 입력: `라인트레이서`
호환성 검사: `Arduino Uno`와 `HC-SR04 초음파 센서`
```

### 기대 결과

```text
라인트레이서 제작에 필요한 Arduino Nano, 적외선 라인 센서, DC 기어모터, 모터 드라이버, 배터리, 섀시, 바퀴와 총 예상 비용 62,600원이 표시됩니다.
호환성 검사에서는 전압, 전류, 인터페이스가 PASS로 표시되고 호환 가능하다는 결과가 나타납니다.
```

### 발표 문장

> 먼저 기기 입력란에 `라인트레이서`를 입력합니다.
> **필요 부품 확인** 버튼을 누르면 관련 프로젝트와 필요한 부품의 수량, 예상 비용이 나타납니다.
>
> 이 결과는 입력값을 프로젝트명과 설명, 등록된 부품 정보에 비교하는 규칙에 따라 만들어졌습니다.
> 이어서 두 부품을 선택하면 전압 범위, 전류, 공통 인터페이스, 축 직경을 검사하고 경고 이유도 함께 보여 줍니다.
>
> 사용자는 결과를 참고해 프로젝트 상세를 보거나 실제 부품 설명서를 확인한 뒤 제작 여부를 직접 결정할 수 있습니다.

## 5. AI 또는 AI적 판단 방식

### 판단 흐름

```text
사용자의 입력
→ 입력값 검사
→ 규칙 또는 점수 계산
→ 결과와 판단 이유 표시
→ 사용자가 최종 결정
```

### 우리 프로젝트의 판단 흐름

```text
기기명 또는 부품 선택
→ 입력값과 등록 데이터 확인
→ 키워드 매칭 또는 호환성 규칙 계산
→ 결과와 판단 이유 표시
→ 사용자가 최종 결정
```

### 발표 문장

> 저희 프로젝트는 실제 생성형 AI API 대신 **조건문, 키워드 매칭, 점수 계산, 미리 작성한 데이터 목록**을 사용했습니다.
>
> 사용자가 기기명을 입력하면 프로젝트명·설명·부품 정보에 포함된 키워드를 비교하고, 관련 점수가 높은 프로젝트를 최대 3개 보여 줍니다.
> 호환성 검사는 전압 범위가 겹치는지, 공통 인터페이스가 있는지, 축 직경이 같은지를 확인합니다.

## 6. 왜 ‘무해한 AI’인가?

### 확인 항목

- 개인정보를 수집하지 않는가?
- 특정 사람이나 집단을 차별하지 않는가?
- 혐오·폭력·위험 행동을 추천하지 않는가?
- 판단의 한계를 사용자에게 알리는가?
- 사용자가 최종적으로 결정할 수 있는가?

### 발표 문장

> 이 기능이 잘못 판단하면 맞지 않는 부품을 연결하거나 필요한 부품을 빠뜨릴 수 있습니다.
> 이를 예방하기 위해 조건별 결과와 경고를 표시하고, 결과가 안전을 보증하지 않는 참고 정보임을 명시했습니다.
>
> 또한 AI의 결과를 정답으로 강요하지 않고  
> 사용자가 부품 설명서를 추가로 확인하고 제작 또는 구매 여부를 직접 선택할 수 있게 만들었습니다.
>
> 이러한 점에서 저희 프로젝트는 사람에게 도움을 주면서도  
> 위험을 줄이는 ‘무해한 AI’를 표현합니다.

## 7. AI 코딩 도구 활용

### 가장 도움이 된 요청

```text
현재 앱의 실제 기능을 분석해 프로젝트 계획서와 발표 스크립트를 구현과 일치하도록 수정하고, 변경 후 API와 오류 상황을 테스트해 주세요.
```

### 요청에 포함한 내용

- 구현할 기능: 기기 입력 기반 부품 안내와 안정적인 API 오류 처리
- 수정할 파일: `server.js`, `public/index.html`, `public/app.js`, `public/style.css`, 문서 파일
- 변경하면 안 되는 부분: 기존 프로젝트·호환성·구매처 기능의 동작
- 완료 기준: 기기 입력 시 부품과 비용 표시, 빈 입력과 서버 오류 안내
- 테스트 기준: 정상 입력, 빈 입력, 미등록 기기, 404 응답 확인

### AI 결과에서 발견한 문제

> 공통 응답 처리 함수와 오류 메시지를 추가한 뒤 정상·빈 입력 API를 다시 테스트했습니다.

## 8. 테스트와 오류 수정

### 대표 테스트

| 입력 또는 조작 | 기대 결과 | 실제 결과 | 통과 여부 |
|---|---|---|:---:|
| `라인트레이서` 입력 후 버튼 클릭 | 관련 부품과 예상 비용 표시 | 관련 프로젝트와 부품 7종, 62,600원 표시 | [x] |
| 빈 기기명으로 버튼 클릭 | 입력 안내 표시 | 기기 이름 입력 안내 표시 | [x] |
| `피아노` 입력 | 등록 데이터 없음 안내 | 관련 기기를 찾지 못했다는 안내 표시 | [x] |

### 발견한 오류

- 재현 순서: 기기명을 입력하고 필요 부품 확인 버튼을 클릭한다.
- 기대 결과: JSON 결과가 화면에 표시된다.
- 실제 결과: `Unexpected end of JSON input` 오류가 표시되었다.
- 오류 원인: 빈 응답 또는 JSON이 아닌 응답을 바로 `response.json()`으로 파싱했다.
- 수정 방법: 응답 본문을 먼저 읽고 JSON 여부와 HTTP 상태를 확인하는 `requestJson` 함수를 추가했다.
- 다시 테스트한 결과: 정상 입력은 200 JSON, 빈 입력은 400 JSON으로 처리되었다.

### 발표 문장

> 테스트 과정에서 **[오류]**를 발견했습니다.  
> 기대한 결과는 **[기대 결과]**였지만 실제로는 **[실제 결과]**가 나타났습니다.
>
> 원인은 **[원인]**이었고, **[수정 방법]**으로 해결했습니다.  
> 수정한 뒤 동일한 조건에서 다시 테스트해 정상 작동을 확인했습니다.

## 9. 역할과 마무리

### 역할

- 팀원 1: 정영운, 드라이버로 기능 구현과 실행 담당
- 팀원 2: 신동석, 내비게이터로 요구사항·코드·테스트 검토
- 드라이버와 내비게이터 교대 방법: 기능 단위로 역할을 바꾸고 두 사람이 결과를 함께 확인

### 발표 문장

> **정영운**은 주로 기능 구현과 실행을 담당했고,
> **신동석**은 요구사항 확인과 코드·테스트 검토를 담당했습니다.
>
> 개발 중에는 드라이버와 내비게이터 역할을 교대하며  
> 코드와 AI의 답변을 함께 검토했습니다.
>
> 이번 프로젝트를 통해 규칙 기반 기능도 결과의 근거와 한계를 함께 설명해야 한다는 점을 배웠습니다.
> 시간이 더 있다면 사용자가 보유한 부품 수량을 입력해 부족한 부품과 추가 비용을 계산하는 기능을 추가하고 싶습니다.
> 이상으로 발표를 마치겠습니다.
